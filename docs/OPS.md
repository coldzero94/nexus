# 크래시·안정성 운영 (E8-3, #48)

기준일 2026-07-20. 2인 팀 전제 — 온콜 없음, **주간 확인 루틴**으로 운영한다.

## 1. 수집 구성

| 채널 | 역할 | 상태 |
|---|---|---|
| **Sentry** (무료 5k 에러/월) | 미처리 크래시 + **처리된-실패**(occurrence-only) | 래퍼 `app/crash/CrashReporting.kt`. DSN 미설정 시 완전 no-op |
| **Play vitals** | ANR율·크래시율의 공식 기준(스토어 노출·검색 랭킹에 반영) | Play Console → 품질 → Android vitals. 계정 개설(E8-5) 후 자동 |

- Sentry 프로젝트 생성(무료 가입) → DSN을 `kotlin/gradle.properties`(미커밋) 또는 CI 시크릿에 `nexus.sentry.dsn`으로 주입. 없으면 초기화 자체를 안 한다(동의 전 자동 수집 없음 — Crashlytics를 배제한 이유와 같은 원칙).
### 처리된-실패 (#239)

미처리 크래시만 보면 **저하된 성공**이 안 보인다. "동기화가 3일째 원장 DB 오류로 실패 중" 같은 상태는 예전엔 `Log.w`로 logcat에만 남아, 원격 테스터 폰에선 USB 없이 확인이 불가능했다 — 알파의 목적이 학습인데 그 학습이 유실됐다.

- 보내는 것은 **`FailureCategory` 이름 하나뿐**이다. 예외 메시지·스택·수치는 싣지 않는다(메시지엔 값이 섞일 수 있다 — 불변식 ②). 신호 목록은 `FailureCategoryTest`가 고정해, 늘리려면 리뷰를 거쳐야 한다.
- Sentry에서 `handled:` 접두어로 미처리 크래시와 분리해 본다. 레벨은 WARNING.
- 대응이 갈리는 유일한 분류는 **`SYNC_PERMISSION`** — 사용자 조치가 필요하고, 나머지는 재시도로 회복된다. `LEDGER_DB`는 crown jewel이 걸려 가장 무겁게 본다.
- 기기에도 **마지막 분류 + 연속 실패 횟수**를 남긴다(`TokenStore`). DSN이 없는 알파 초기에도, 테스터 폰을 손에 들었을 때 즉석에서 판단할 수 있어야 한다. 성공하면 카운터를 지운다 — 회복 여부도 신호다.

- SDK 직접 호출은 detekt `ForbiddenImport`가 차단 — 모든 옵션(tracing off, PII off, 스크린샷·뷰 계층 첨부 금지)은 래퍼가 강제한다. **화면에는 건강 파생 표시값이 있으므로 스크린샷 첨부는 절대 켜지 않는다.**

## 2. 주간 루틴 (금요일, 담당 교대)

1. Sentry Issues — 신규 크래시 확인: 발생 수 상위부터, **재현 경로를 이슈(버그 템플릿)로 등록**하고 보드 Backlog에.
2. Play vitals — **나쁜 동작 임계치** 확인: 사용자당 크래시율 1.09%·ANR율 0.47% 초과 시 스토어 노출 불이익. 초과 항목은 그 주 최우선 티켓.
3. 무료 티어 소진 확인(Sentry Stats) — §3 초과 대응.

4. **알파 기간(D0~D14)에만**: 테스터에게 설정 화면의 "이번 주 연 날짜"를 **DM으로** 물어 로컬 로스터를 갱신(주 2 값은 주말을 포함해야 하므로 금요일이 아니라 **D13(일요일)에 확정 수집** — 카운터가 최근 7일 이동창이라 D13에 읽어야 주 2(D7~D13)와 정확히 맞는다). TelemetryDeck 활성 추세로 개연성 대조. **D14에 go/no-go를 #74 이슈 코멘트로 기록(집계만)**. 채워진 로스터·개인별 수치는 **공개 레포에 커밋하지 않는다** — 정의·게시 규칙은 [ALPHA.md](./ALPHA.md).

초기 소규모(테스터 12명)에서는 vitals 임계 표본이 안 잡히므로 **Sentry가 1차 신호**, vitals는 공개 출시 후 주 신호로 승격.

## 3. 무료 티어 초과 시 (STACK.md §8)

1. **크래시 루프 의심 먼저** — 같은 스택이 수백 건이면 수집량 문제가 아니라 버그. 핫픽스 우선.
2. Sentry 프로젝트 설정 → Client Keys → **Rate Limit** 설정(예: 분당 5)으로 루프 방어.
3. 상시 초과면 수집 다이어트(환경 필터, 이슈별 mute) → 그래도 부족하면 vitals 단독 회귀(코드는 DSN 제거만).

## 5. 의존성 취약점 트리아지 (#244)

**수집**: `.github/workflows/dependency-scan.yml`이 주 1회(월 09:00 KST)와 락파일 변경 PR에서 OSV-Scanner를 돌린다. Dependabot(`.github/dependabot.yml`)은 같은 요일에 갱신 PR을 연다 — 월요일에 둘을 함께 본다.

**스캔 대상**: `kotlin/app/gradle.lockfile`(런타임 클래스패스 전용). 전 configuration을 잠그면 Gradle·AGP가 끌어오는 빌드 도구(netty·bouncycastle 등) CVE가 결과를 뒤덮는데, 그것들은 **앱에 출하되지 않아** 사용자 위험이 아니다. **락은 버전을 `strictly`로 고정**하므로, 카탈로그에서 버전을 올려도 락파일을 갱신하지 않으면 옛 버전이 그대로 쓰인다(빌드는 조용히 통과 — 실측). 의존성을 바꾼 뒤에는 반드시 `./gradlew :app:dependencies --write-locks`를 돌리고, Dependabot PR도 이 갱신을 포함해야 한다.

**트리아지 순서**:
1. **출하 여부** — 락파일에 있으면 앱에 들어간다(빌드 도구는 애초에 제외됨).
2. **경로 도달성** — 우리 코드가 그 취약 함수를 부르는가. 예: `FileBackedOutputStream` 같은 서버측 API는 앱에서 호출 경로가 없다.
3. **직접 vs 트랜지티브** — 직접 의존이면 버전을 올린다. 트랜지티브면 상위 SDK 갱신을 기다리거나, 급하면 `constraints`로 강제 상향(호환성 리스크는 우리가 진다).
4. **결정 기록** — 조치했든 수용했든 이 문서 아래 표에 남긴다. "봤는데 넘어갔다"가 기억에만 있으면 다음 사람이 같은 판단을 반복한다.

**차단 승격 기준**: 지금은 advisory-only(빌드 통과)다. ① 아래 표가 비고 ② 새 취약점이 주 1건 이하로 안정되면 `continue-on-error`를 제거해 차단으로 올린다.
