# 알파 게이트 측정 (#229, E15-1)

기준일 2026-07-27. **게이트 판정의 단일 기준 문서** — MVP §9·SPRINTS의 "D14에 테스터 절반이 주 3회+ 오픈"을 측정 가능한 절차로 고정한다. 정의가 없으면 게이트는 주관적 인상으로 붕괴하고, 게이트 측정 가능성이 곧 알파의 존재 이유다.

관련: `docs/MVP.md §9`(로드맵·게이트) · `docs/SPRINTS.md`(게이트와 그 이후) · `docs/OPS.md §2`(주간 루틴) · #74(closed test 14일 시계 운영)

## 1. 조작적 정의

| 용어 | 정의 |
|---|---|
| **판정창** | closed test 개시일(#74 D0)부터 **14일**. D0은 첫 테스터가 스토어 설치 링크를 받은 날. |
| **주** | **ISO 주**(월요일 시작). 판정창은 보통 두 개의 부분 주에 걸치므로, 아래 "주 1/주 2"는 D0~D6, D7~D13의 **7일 구간**을 뜻한다(달력 주가 아니라 코호트 주 — 테스터마다 시작일이 달라도 동일 기준). |
| **오픈 1회** | 그 날짜에 `APP_OPENED`가 **한 번 이상** 발생. 같은 날 여러 번 열어도 1회로 센다(빈도 조작 방지). |
| **주 3회+** | 한 7일 구간에서 `APP_OPENED`가 발생한 **서로 다른 날짜 수 ≥ 3**. |
| **절반** | 옵트인 테스터 **12명 중 ≥ 6명**이 주 2(D7~D13)에서 "주 3회+"를 만족. 주 1은 온보딩 신기함이 섞이므로 참고 지표로만 본다. |
| **게이트 통과** | 위 "절반" 충족. 미충족 시 S8+로 가지 않고 코어 루프를 고친다(SPRINTS). |

**중도 이탈자 처리**: 기기 교체·앱 삭제 등으로 측정이 끊긴 테스터는 **분모에 남긴다**(12명 고정). 이탈도 게이트가 재려는 신호의 일부다. 다만 로스터 비고란에 사유를 적어 no-go 원인 분석에 쓴다.

## 2. 2단 리드아웃

계측 하나에 판정을 걸지 않는다 — 익명 집계는 개인 식별이 불가하고, 수동 로스터는 표본이 작아 서로를 보완한다.

| 단 | 소스 | 역할 | 한계 |
|---|---|---|---|
| **① 집계 프록시** | TelemetryDeck 주간 활성 사용자 | 추세·이상 감지(급락·0 유입) | **사용자별 날짜 수를 못 뽑는다**(익명 집계) → 게이트 판정에 단독 사용 불가 |
| **② 수동 로스터** | 아래 템플릿(2주 × 12행) | **authoritative** — go/no-go는 이것으로 판정 | 자기보고 기반이라 성실성 의존 |

**왜 수동인가**: 사용자별 오픈 날짜를 세려면 기기별 식별자를 계측에 실어야 하는데, 그건 익명 원칙(occurrence-only)과 충돌한다. 12명 규모에서는 수동 확인이 더 싸고 정확하며, 공개 출시 후에는 Play Console의 리텐션 코호트가 이 역할을 대체한다.

## 3. 로스터 템플릿

`docs/assets/alpha-roster.csv`를 복사해 쓴다. 매주 금요일에 채우고, 값은 **그 주에 앱을 연 서로 다른 날짜 수**(0~7).

```
tester_id,week1_days,week2_days,week2_meets_3plus,note
T01,,,,
...
T12,,,,
```

- `tester_id`: 실명·연락처를 적지 않는다(T01~T12 익명 ID, 매핑표는 팀 비밀번호 관리자에).
- `week2_meets_3plus`: `week2_days >= 3`이면 `Y`.
- `note`: 이탈·기기 교체·설치 실패 등 판정에 영향을 준 사정.

**집계**: `week2_meets_3plus == Y` 개수 ≥ 6 → **go**.

## 4. 주간 절차 (OPS §2에 편입)

D0~D14 동안 금요일 루틴에 아래를 추가한다.

1. 테스터 채널에 **"이번 주 며칠 여셨어요?"** 한 줄 질문(선택지 0~7). 강요하지 않고, 무응답은 다음 항목으로 보정.
2. TelemetryDeck 주간 활성으로 **응답 총합의 개연성**을 대조(응답 합이 활성과 크게 어긋나면 재확인).
3. 로스터 CSV 갱신 → 레포에 커밋(익명 ID만 담기므로 커밋 가능).
4. **D14 당일**: 로스터로 go/no-go를 판정하고 **#74 이슈에 코멘트**로 기록한다 — 판정 결과, 12명 중 충족 인원, 특이사항(이탈 사유), 그리고 no-go면 다음에 고칠 코어 루프 가설.

## 5. 리텐션 코호트 정의

게이트와 별개로 추세를 남긴다(공개 출시 전 기준선).

- **코호트 기준**: 설치 주(ISO 주). 테스터는 전원 같은 주에 들어오므로 알파 기간엔 단일 코호트.
- **관측 지점**: **D1 · D3 · D7 · W1 · W2** — 각 지점에서 `APP_OPENED`가 1회 이상 발생한 사용자 비율.
  - D1/D3/D7 = 설치 후 경과일 기준, W1/W2 = 코호트 주 1·2에 **한 번이라도** 열었는지(주 단위 잔존).
- **읽는 법**: D1 급락은 온보딩·권한 문제, D7 유지 후 W2 급락은 코어 루프의 반복 동기 부족을 시사한다. no-go 시 이 모양으로 원인 가설을 좁힌다.

## 6. 계측 불변식 (변경 금지)

- 이 문서의 어떤 측정도 **새 이벤트를 요구하지 않는다** — 기존 `APP_OPENED`(occurrence-only)로 충족한다.
- 이벤트를 추가해야 한다면 `TelemetryEvent` enum + `TelemetryPolicyTest`의 고정 allowlist를 **같은 커밋에서** 갱신한다(CI가 강제).
- 페이로드에 건강 파생값(걸음·운동 시간·심박·XP·컨디션·레벨)·원시 타임스탬프·개인 식별자를 싣지 않는다. 날짜 수 집계는 **기기 밖으로 나가지 않는 수동 로스터**가 담당한다.
